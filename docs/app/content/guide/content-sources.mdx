# Content Sources

Use content sources when the Markdown you want to publish already belongs elsewhere in a repository: ADRs, package guides, changelogs, or shared documentation. Ardo materializes a read-only route view during the build while the original file remains canonical.

## Map a Directory

```ts
import { defineArdoConfig } from "ardo/config"

export default defineArdoConfig({
  title: "Workspace Docs",
  content: [{ from: "../../adr", to: "decisions" }],
})
```

An `../../adr/0001-routing.md` source becomes `/decisions/0001-routing`. Existing frontmatter stays intact; otherwise Ardo derives a title from the first heading or filename and uses a numeric filename prefix as sidebar order.

## What Participates

Mapped Markdown and MDX become ordinary generated routes. They participate in the sidebar, section search, sitemap, LLM text output, redirects, internal-link checking, and [frontmatter validation](/en/guide/frontmatter).

## Generated-File Boundary

Ardo writes mapped files under the selected `to` directory and marks it as generated. Edit the original source, never the materialized route. The plugin refuses to delete a non-empty handwritten target directory, so use a dedicated prefix such as `decisions/`.

## Content From Another Repository

Content sources read local files only. To publish docs that live next to code in another repository, check that repository out inside the project before the build, then map it like any other directory:

```yaml
# .github/workflows/docs.yml
steps:
  - uses: actions/checkout@v7
  - uses: actions/checkout@v7
    with:
      repository: example/engine
      ref: 4f9c2b7e1d3a8c6b5e0f2a9d7c4b1e8f3a6d5c20 # a full commit keeps builds reproducible
      path: vendor/engine
  - run: pnpm install --frozen-lockfile
  - run: pnpm build
```

```ts
import { defineArdoConfig } from "ardo/config"

export default defineArdoConfig({
  title: "Product Docs",
  content: [{ from: "vendor/engine/docs", to: "engine" }],
})
```

`from` resolves against the project root. For a private repository, pass a token with read access through the checkout action's `token` input. For local development, clone the repository to the same path and add that path to `.gitignore`. A Git submodule at that path works too; check it out in CI with `submodules: true` instead of the second step.

## Boundaries

Content sources intentionally do not fetch remote URLs, act as a CMS, or transform arbitrary file types. They map local files; [schema-backed collections](#schema-backed-collections) add validation and typed records on top. For content in another repository, [check it out before the build](#content-from-another-repository).

## Schema-Backed Collections

Use `collections` when the same local Markdown set should both materialize into routes and be available to a custom React route as typed build data:

```ts
import { defineArdoConfig } from "ardo/config"
import { defineCollection } from "ardo/vite"

const recipes = defineCollection<{ title: string }>({
  from: "../../recipes",
  to: "recipes",
  schema: (data) => ({ title: String(data.title) }),
})

export default defineArdoConfig({ title: "Docs", collections: { recipes } })
```

Import `getCollection<T>()` from `virtual:ardo/collections` in a custom route to read typed generated records:

```tsx
import { getCollection } from "virtual:ardo/collections"

const recipes = getCollection<{ title: string }>("recipes")
```

Collections remain local and static: the schema runs during the build, while the generated route pages continue through the normal sidebar, search, sitemap, redirect, and LLM pipelines. Source paths are project-relative, so the virtual module does not expose an author's absolute filesystem paths.

Add these options to the version-matched [Basic example](/en/guide/agent-instructions#the-basic-example). The authored files stay canonical: the build generates the `/recipes/*` pages from them, and a custom React route can render the same records.
