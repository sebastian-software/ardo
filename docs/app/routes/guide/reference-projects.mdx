# Basic Example

Ardo maintains one public example at `examples/basic`. It is a small static site
with Markdown/MDX pages, search, and an interactive React component. The same
application setup supports product documentation, library reference, and docs
for multiple packages. Add only the optional features your project needs.

## Use the Matching Release

Open the [Git tag](https://github.com/sebastian-software/ardo/tags) matching your
exact installed version: `ardo-v<version>`. Read `examples/basic` in that tag.
For Ardo development, use the example and built package from the same checkout
revision as these instructions.

When copying the example into an independent project, replace its
`ardo: workspace:*` dependency with that released version. Keep compatible
dependency versions from the tag and use your own lockfile. With pnpm, add the
minimal esbuild build-script policy shown in the example README and
[manual installation](/guide/getting-started#manual-installation).

The README explains how to run the example, which files to edit, and which files
are generated. [Agent Instructions](/guide/agent-instructions) cover setup,
adoption, and upgrades.

## API Documentation

Add the optional native compiler dependencies and configure `api` in
`ardo.config.ts`. For a single TypeScript project:

```ts
import { defineArdoConfig } from "ardo/config"

export default defineArdoConfig({
  title: "My Documentation",
  githubPages: false,
  api: {
    entryPoints: ["./src/index.ts"],
    tsconfig: "./tsconfig.api.json",
  },
})
```

[Native API Documentation](/guide/api-documentation) explains installation,
TypeScript configuration, development updates, and supported types.

## Multiple Packages

Use an `api` array when packages need different TypeScript configurations or API
route prefixes. Each entry selects its source entry points, TypeScript config,
and distinct output directory. This changes the inputs to API generation; it
does not require a different documentation application.

API generation reads the selected TypeScript projects separately from the
application bundle. Keep the docs application's own dependencies declared and
installed in its package. To use a component from another workspace package,
install that packaged dependency in the docs package; do not import sibling
component source through filesystem paths or aliases.

See [Multiple packages](/guide/api-documentation#multiple-packages) for the
configuration and compiler boundaries.

## Content Owned Elsewhere

Add `content` mappings to publish Markdown owned outside `app/routes/`. Use
`collections` when a React page also needs typed, static frontmatter records
from the same files. The authored source stays canonical; materialized routes
are generated output. Follow [Content Sources](/guide/content-sources).

## Deployment

Choose the hosting target explicitly. GitHub repository detection can derive a
Pages subpath, but a GitHub remote alone does not establish where you deploy.
GitHub Pages with a custom domain and other hosts can serve from the domain
root. Follow [Deployment](/guide/deployment) for base paths, prerendered routing,
and CI workflows. Provider configuration stays outside the common example.

## Validation

`pnpm test:integration` typechecks and builds Basic and applies focused API,
multiple-project, collection, GitHub Pages, runtime, and bare-layout fixtures.
Basic and the optional API configuration also install, typecheck, and build as
isolated consumers of the packed Ardo package. CI runs integration checks on
Node.js 22, 24, and 26; browser checks cover development and production preview.

These checks live under `tests/`; the example contains only application source,
configuration, and its README. Internal fixtures are regression inputs rather
than additional setup references.
