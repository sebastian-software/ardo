# Agent Instructions

These instructions cover Ardo 6. Use them for a new documentation site, an existing React repository, or an upgrade. Ardo 6 does not ship `create-ardo`.

## Match the Version First

Read the repository's manifest and lockfile to identify its installed Ardo version. For a new site, target Ardo 6 explicitly. Use `https://ardo-docs.dev/v6/llms.txt` as the documentation index and `https://ardo-docs.dev/v6/llms-full.txt` for the complete Markdown instructions. The unversioned text files follow the current documentation version and can change when another major is released.

Read `examples/basic` from the matching `ardo-v<exact-version>` Git tag in [Ardo's repository](https://github.com/sebastian-software/ardo/tags). For example, Ardo `6.0.0` uses `ardo-v6.0.0`. Do not combine a released package with examples from `main`. During development, use the instructions, examples, and built package from the same checkout revision.

When upgrading from another major, read that major's documentation and the target major's migration guidance before changing configuration. If a matching release tag or instruction is unavailable, report the gap rather than guessing from a different version.

## Inspect the Repository

Check the package manager, workspace layout, Node.js version, dependency versions, `ardo.config.*`, Vite configuration, React Router configuration, application root, routes, styles, and deployment workflow. Ardo needs Node.js 22.22.0 or newer and a supported native target with optional dependencies enabled.

Use the version-matched [Basic example](/guide/reference-projects) at
`examples/basic` as the shared application setup. Read its README, manifest,
configuration, and app files. Its README identifies the authored source,
generated files, and commands for both workspace and independent use.

Select optional features by the project's needs:

| Need                                                      | Configuration guide                                             |
| --------------------------------------------------------- | --------------------------------------------------------------- |
| API reference for one TypeScript project                  | [Native API Documentation](/guide/api-documentation)            |
| API reference for multiple packages                       | [Multiple packages](/guide/api-documentation#multiple-packages) |
| Markdown outside the route tree or static collection data | [Content Sources](/guide/content-sources)                       |
| Hosting and base-path settings                            | [Deployment](/guide/deployment)                                 |

A monorepo changes API inputs, not the documentation application's runtime
boundary. Declare and install the docs package's dependencies locally. Import
workspace components through an installed packaged dependency, not sibling
source paths. API generation can read separately configured TypeScript projects.

A setup skill should use these versioned instructions and the same Basic
example, then add the selected feature configuration. Keep setup rules here
instead of maintaining separate skill templates.

## Make the Smallest Compatible Change

State the example revision, files to add or change, validation commands, and unresolved choices before editing. Follow the repository's instructions and the requested scope. Ask for direction when a necessary change affects existing application behavior or deployment ownership.

For a **new site**, adapt the basic reference into the requested directory. Replace `workspace:*` with an explicit released Ardo 6 dependency, let Ardo manage its React, router, and Vite versions, and use the chosen package manager's lockfile. The workspace example uses `workspace:*` only inside Ardo's own repository. With pnpm, allow esbuild's build script as shown in [manual installation](/guide/getting-started#manual-installation); do not copy Ardo's entire workspace policy. Set a custom site title in optional `ardo.config.ts`, add the authored routes, then adapt the deployment configuration to the requested host.

For an **existing project**, introduce Ardo around documentation routes. Merge the necessary dependencies and move Ardo's options into optional `ardo.config.ts` with `defineArdoConfig` from `ardo/config`. Preserve custom Vite plugins and settings in `vite.config.ts`; the Ardo CLI adds its own framework integration without an `ardo()` plugin call. Preserve customized root/layout code, providers, component systems, styles, routes, workspace policy, and deployment choices. See [Adopt Ardo in an Existing Project](/guide/adopt-ardo).

For an **upgrade**, update the dependency and documented integration changes. Compare the existing setup with the matching target example. Preserve authored content and application-specific behavior; do not replace framework entry files wholesale.

`app/routes.ts`, generated API routes, and materialized collection routes are build output. Do not edit them by hand. Native API documentation is opt-in; add its native compiler alias, `oxc-parser` dependency, and API configuration only when the project needs it. Follow [Native API Documentation](/guide/api-documentation) for the matching dependency versions. Use `ardo dev`, `ardo build`, and `ardo preview` for the managed toolchain. Import React APIs from `ardo/react`, router APIs from `ardo/router`, Vite configuration helpers from `ardo/vite`, and the `ReactRouterConfig` type from `ardo/config`. Set `jsxImportSource` to `ardo` and use `ardo/vite/client` in TypeScript's `types` list. The basic reference only requires Ardo at runtime; TypeScript remains a development tool. The default client entry comes from React Router. The server entry re-exports `default` and `streamTimeout` from `ardo/entry.server`; retain it so React Router does not add `isbot` to the project. Tailwind is optional; retain the repository's styling choice.

## Validate and Report

Install dependencies with the repository's package manager. Run its applicable typecheck and tests, then build the site. For an existing application, also run the checks that protect its existing routes. If a check is unavailable, say which behavior remains unverified.

Inspect the generated HTML for the home page and an authored documentation route. Verify generated API or collection pages when enabled. Start the local development server and check that navigation works and the browser reports no runtime errors. Build success alone does not establish that an existing application's integration is correct.

Report the files changed, dependency version, selected reference tag or checkout revision, validation results, and any remaining gaps. Do not deploy or change hosted-service ownership unless requested.

Ardo's CI runs `pnpm test:integration` against Basic and focused internal feature fixtures. Basic and its optional API configuration also install, typecheck, and build against the packed Ardo package outside the workspace. Browser checks cover development and preview. These checks validate the executable setup; they do not evaluate every agent's interpretation of these instructions.
