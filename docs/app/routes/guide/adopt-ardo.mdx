# Adopt Ardo in an Existing Project

Ardo fits into an existing React, Vite, and React Router repository. Do not regenerate the project or replace its component system. Give a coding agent this instruction together with the repository:

```text
Add Ardo 6 documentation to this repository. Read https://ardo-docs.dev/v6/llms.txt first, then follow https://ardo-docs.dev/v6/guide/agent-instructions and the adoption guide. Inspect the project, adapt the tested Basic example from the matching Ardo release tag, preserve existing routing, components, styles, and deployment choices, and run the applicable checks.
```

`/v6/llms.txt` is a concise map of the Ardo 6 documentation; `/v6/llms-full.txt` contains the complete Markdown context. Both are generated with the versioned docs build. The unversioned aliases follow the current major. [Agent Instructions](/guide/agent-instructions) define the shared setup and upgrade workflow.

## Start from the Basic Example

Read the version-matched [Basic example](/guide/reference-projects) for the common
application setup. Add [API documentation](/guide/api-documentation),
[external content](/guide/content-sources), or [deployment settings](/guide/deployment)
only when the project needs them.

The example's README identifies editable files, generated-file boundaries, and
validation commands. Preserve customized application behavior while adapting it.

## Agent Workflow

1. Inspect `package.json`, the workspace layout, `ardo.config.*`, `vite.config.*`, `react-router.config.*`, the app root, existing routes, and deployment workflow.
2. Read this guide, [Getting Started](/guide/getting-started), [Configuration](/guide/configuration), and the Basic example.
3. State a plan naming every file to add or change, the example revision, and any assumption that cannot be verified.
4. Follow the repository's instructions and requested scope, resolve choices that change application behavior or deployment ownership, and make the smallest compatible change.
5. Run the repository's applicable validation commands and report their results.

## Safety Boundaries

Never silently replace a customized `app/root.tsx`, providers, design-system components, deployment configuration, route model, workspace policy, credentials, or hosted-service choices. When a reference and the project disagree, retain the project choice and explain the adaptation. Ask for direction when a decision changes runtime behavior or deployment ownership.

## Adopt or Migrate

For adoption, follow [Getting Started](/guide/getting-started#manual-installation) and introduce Ardo around documentation routes rather than replacing the application shell. Use [Content Sources](/guide/content-sources) for Markdown owned elsewhere in the repository and [Native API Documentation](/guide/api-documentation) for API pages.

For an existing Ardo project, switch package scripts to `ardo dev`, `ardo build`, and
`ardo preview`. Import Vite helpers from `ardo/vite`, the router configuration type from
`ardo/config`, React APIs from `ardo/react`, and routing APIs from `ardo/router`. Set
`jsxImportSource` to `ardo` and replace `vite/client` with `ardo/vite/client` in TypeScript
configuration. Move Ardo's site and integration options to optional `ardo.config.ts` with
`defineArdoConfig` from `ardo/config`. Remove the `ardo()` Vite plugin when the site no longer
needs a custom Vite config; keep `vite.config.ts` for additional Vite plugins or Vite-specific
settings. A standard client entry can be removed to use React Router's default. Replace a standard
server entry with `export { default, streamTimeout } from "ardo/entry.server"`; preserve
customized entry behavior and use Ardo's React DOM and router entry points.
Once direct tooling imports have been migrated, remove the site's React, React DOM, router,
Vite, icon, and related type dependencies that Ardo now owns. Keep other application
libraries and optional integrations declared locally. Ardo resolves React and router
imports to its own installation, including imports in installed component libraries.

Compare configuration and route layout with the matching current reference. Keep project-specific root/layout code and update only the framework integration, generated-route boundary, and documented configuration fields that differ. Run at least:

```bash
pnpm typecheck
pnpm test
pnpm build
```

Run only commands the repository defines; report missing checks. Use `CI=true` for non-interactive pnpm environments. Ardo 6 uses the same versioned instructions and Basic example for new sites and existing projects.

## Style Documentation in an Existing Design System

Map the public `--ardo-*` theme variables first. Use the stable classes below for
layout and reading styles that need more than token changes. Generated class
names from Ardo's stylesheet are implementation details.

| Region                                | Styling hooks                                                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Document grid and optional right rail | `.ardo-doc-page`, `.ardo-page-rail`, `.ardo-page-rail-section`                                                    |
| Article and introduction              | `.ardo-content`, `.ardo-content-header`, `.ardo-content-title`, `.ardo-content-description`, `.ardo-content-body` |
| Sidebar slots                         | `.ardo-sidebar`, `.ardo-sidebar-tabs`, `.ardo-sidebar-panel`, `.ardo-sidebar-header`, `.ardo-sidebar-nav`         |
| Page outline                          | `.ardo-toc`                                                                                                       |
| Code sheets                           | `.ardo-code-block`, `.ardo-code-title`, `.ardo-code-wrapper`, `.ardo-copy-button`                                 |

Scope overrides to the application's own wrapper. These classes retain Ardo's
default styling and do not select a different theme. A site that already offers
section navigation can hide `.ardo-sidebar-tabs` and retain the sidebar's reading
links. Keep every section reachable through the site's own navigation on desktop
and mobile.

Set `scrollMode="document"` on `ArdoRoot` when your site owns the header or footer, or when the
documentation should use normal document scrolling. The sidebar and right rail stick below
`--ardo-layout-headerHeight`, which you can set once on `ArdoRootLayout` and change at a mobile
breakpoint. A sticky site header stays in document flow; a fixed header needs its height reserved
once in the site wrapper. See [Site UI Configuration](/guide/site-ui#document-scrolling-with-site-owned-chrome)
for a complete example. `ArdoRoot.className` can still replace the default layout class without
disabling document scrolling.

Use `ArdoRootLayout.className` for theme variables that also need to reach
body-level portals such as search. A custom `favicon` can point to SVG, PNG,
or ICO; Ardo leaves its MIME type to the response.
